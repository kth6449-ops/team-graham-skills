## 0. 확장 배경 및 원칙

### 왜 확장하는가
BESOLT의 제품(SOLT-AI / SOLT-BI)은 근본적으로 **"현장 데이터 → 지표화 → 의사결정"** 구조다.
이 구조는 제조업 고유가 아니라 **모든 SME의 운영 문제에 동일하게 적용**된다.

```
제조업        설비 가동 데이터  → OEE       → 생산성 개선
유통/물류     피킹·출고 데이터  → 처리율     → 물류비 절감
건설          공정·투입 데이터  → 진도율     → 원가 초과 방지
F&B           판매·재료 데이터  → 원가율     → 마진 개선
전문서비스    투입시간 데이터   → 가동률     → 수익성 개선
```

**핵심 원칙: 지표는 다르지만 구조는 같다.**
설계 시 업종별 지표를 하드코딩하지 말고 **메트릭 정의 추상화 계층**을 둔다.

### 업종 확장 시 3대 금기
1. **제조 용어 그대로 쓰기** — 물류 고객에게 "OEE"라고 하면 신뢰를 잃는다. 업종 언어로 번역할 것
2. **업종 표준·규제 무시** — 헬스케어 개인정보, 건설 안전법, F&B 위생법 등은 요구사항 이전에 제약조건
3. **SME 현실 무시** — 전담 IT 인력 없음, 예산 제한, 기존 시스템 노후 — 이 3가지가 항상 사실

### 1-3. 건설·엔지니어링 (Construction & EPC)

| 항목 | 내용 |
|------|------|
| **핵심 프로세스** | 수주(입찰) → 실행예산 편성 → 공정계획 → 자재/장비 투입 → 시공 → 검측 → 준공 → 하자보수 |
| **핵심 지표** | 공정진도율(계획 vs 실적), 실행예산 대비 투입률, EVM(PV/EV/AC, CPI/SPI), 안전사고율(TRIR), 재시공률 |
| **주요 시스템** | ERP(원가), PMIS(공사관리), BIM, 안전관리시스템 |
| **연동 방식** | REST API, 엑셀 업로드(현실적으로 가장 많음), IoT 센서(안전) |
| **Pain Point** | 현장별 원가 실시간 파악 불가, 공정 지연 조기 감지 실패, 안전 관리 인력 부족 |
| **규제·표준** | 건설산업기본법, 중대재해처벌법, 산업안전보건법, KOSHA-MS |
| **SME 현실** | 현장소장 개인 역량 의존, 원가는 월말에야 확인, 서류 작업 과중 |
| **AI 적용 포인트** | EVM 기반 공기·원가 이탈 조기경보, 안전 영상 분석, 자재 소요 예측, 하자 패턴 분석 |

```
EVM 핵심 공식 (건설 프로젝트 필수)
PV(계획가치) = 계획공정률 × 총예산
EV(획득가치) = 실제공정률 × 총예산
AC(실투입비) = 실제 발생 원가
CPI = EV/AC   (1 미만이면 원가 초과)
SPI = EV/PV   (1 미만이면 공기 지연)
EAC(완료예상원가) = 총예산 / CPI
```

## 2. 업종 공통 추상화 모델 — **설계 시 반드시 적용**

업종별로 지표를 따로 만들지 않는다. **메트릭 정의를 데이터로 관리**한다.

### 2-1. 메트릭 정의 추상화 스키마

```sql
-- 업종 무관 공통 메트릭 정의 테이블
CREATE TABLE metric_definition (
    metric_id       VARCHAR(50) PRIMARY KEY,
    industry_code   VARCHAR(20) NOT NULL,   -- MFG, LOG, CON, HLT, FNB, RET, PRO, SAAS
    metric_name     VARCHAR(100) NOT NULL,  -- 'OEE', '재고회전율', '공정진도율'
    metric_name_en  VARCHAR(100),
    category        VARCHAR(50),            -- productivity, quality, cost, delivery, safety
    formula         TEXT NOT NULL,          -- 산출식 (수식 표현)
    unit            VARCHAR(20),            -- %, 회, 일, 원
    target_value    NUMERIC,
    threshold_warn  NUMERIC,
    threshold_crit  NUMERIC,
    aggregation     VARCHAR(20),            -- sum, avg, ratio, last
    source_tables   TEXT[],                 -- 산출에 필요한 원천 테이블
    refresh_cycle   VARCHAR(20)             -- realtime, hourly, daily, monthly
);

-- 업종 무관 공통 측정값 테이블
CREATE TABLE metric_value (
    time            TIMESTAMPTZ NOT NULL,
    metric_id       VARCHAR(50) REFERENCES metric_definition(metric_id),
    entity_type     VARCHAR(30),   -- equipment, warehouse, site, store, project, account
    entity_id       VARCHAR(50),
    value           NUMERIC,
    status          VARCHAR(10)    -- NORMAL, WARN, CRITICAL
);
SELECT create_hypertable('metric_value', 'time');
```

### 2-2. 업종별 메트릭 매핑 예시

| 공통 카테고리 | 제조 | 물류 | 건설 | F&B | 전문서비스 |
|-------------|------|------|------|-----|-----------|
| **Productivity** | OEE | 시간당 처리량 | 공정진도율 | 테이블 회전율 | 가동률 |
| **Quality** | 수율/Cpk | 피킹 정확도 | 재시공률 | 위생점검 점수 | 재작업률 |
| **Cost** | 제조원가율 | 물류비율 | 실행예산 집행률 | 원가율(Food Cost) | 프로젝트 마진 |
| **Delivery** | 납기준수율 | 출고 리드타임 | 공기 준수율 | 조리 대기시간 | 납기 준수율 |
| **Safety/Risk** | 재해율 | 파손율 | TRIR | HACCP 이탈 | 계약 리스크 |

**설계 규칙: 신규 업종 추가 시 코드 변경 없이 `metric_definition` 행 추가만으로 대응 가능해야 한다.**

## 3. SME 제품개발 시 반드시 고려할 현실 제약

### 3-1. SME 3대 제약 (모든 요구사항 정의 시 전제)

| 제약 | 실태 | 설계 대응 |
|------|------|----------|
| **인력** | 전담 IT 인력 없음, 겸직 담당자 1명 | 관리 UI 최소화, 자동 복구, 무설정 기본값 |
| **예산** | 초기 구축비 민감, 월 고정비 저항 | 단계적 도입(모듈 분리), 명확한 ROI 제시 |
| **레거시** | 노후 ERP, 엑셀 의존, 통신 미지원 설비 | 엑셀 업로드 경로 **필수 제공**, 게이트웨이 방식 수집 |

> **엑셀 업로드는 타협이 아니라 필수 기능이다.**
> SME 프로젝트에서 "API 연동만 지원"은 도입 실패의 가장 흔한 원인이다.

### 3-2. SME 도입 성공 패턴

```
1단계 (1개월)   현행 지표 1~2개만 자동화 → "숫자가 보인다"는 체감 제공
2단계 (2~3개월) 지표 확장 + 이상 알림 → "문제를 먼저 안다"는 가치 제공
3단계 (4~6개월) 예측·추천 → "무엇을 할지 알려준다"는 가치 제공
```

**금기: 1단계부터 AI 예측 모델을 제안하지 말 것.** SME는 기초 데이터 신뢰도부터 확보해야 한다.

### 3-3. 업종별 도입 저항 요인과 대응

| 업종 | 주요 저항 | 대응 논리 |
|------|----------|----------|
| 제조 | "현장이 입력 안 한다" | 자동수집 우선, 입력 최소화 설계 |
| 물류 | "성수기엔 시간 없다" | 비수기 도입, 성수기 효과 검증 |
| 건설 | "현장마다 다르다" | 현장 1곳 파일럿 → 표준화 후 확산 |
| 헬스케어 | "개인정보 문제" | 온프레미스/Edge, 가명처리 설계 제시 |
| F&B | "점주가 못 쓴다" | 모바일 우선, 3탭 이내 완료 UX |
| 리테일 | "채널마다 달라서" | 채널 어댑터 구조, 우선 1채널 검증 |

## 4. 업종 확장 시 요구사항 정의 체크리스트

신규 업종 프로젝트 착수 시 **G1 게이트 전에 반드시 확인**한다.

```markdown
## 업종 진입 체크리스트 (G1 Entry 조건)
- [ ] 해당 업종의 핵심 프로세스 5단계 이상 문서화
- [ ] 업종 표준 지표 5개 이상 정의 (산출식 포함)
- [ ] 데이터 원천 시스템 및 연동 방식 확인 (API/파일/DB직결/수기)
- [ ] **적용 규제·인증 요건 확인** (미확인 시 진행 불가)
- [ ] 고객 현장 인터뷰 3건 이상, Pain Point 우선순위 확정
- [ ] 기존 metric_definition 구조로 수용 가능한지 검토
      → 불가 시 아키텍처 변경 CR 발행
- [ ] 업종 용어집 작성 (제조 용어 → 해당 업종 용어 매핑)
- [ ] SME 3대 제약(인력·예산·레거시) 실태 파악
```

## 5. 업종별 용어 번역 대조표 (고객 커뮤니케이션 필수)

| 우리 용어(제조 기반) | 물류 | 건설 | F&B | 전문서비스 |
|------------------|------|------|-----|-----------|
| 설비 | 창고/설비 | 현장/장비 | 매장/주방 | 프로젝트 |
| 가동률 | 처리 능력 활용률 | 장비 가동률 | 좌석 점유율 | 가동률(빌러블) |
| 생산 실적 | 출고 실적 | 기성 실적 | 판매 실적 | 투입 공수 |
| 불량 | 오출고/파손 | 부적합/재시공 | 폐기/클레임 | 재작업 |

## 6. Senior 레벨 판단 기준 (팀원 공통 적용)

업종 확장 프로젝트에서 시니어는 아래를 **먼저** 판단한다.

```python
SENIOR_JUDGEMENT_ORDER = [
    "1. 규제·인증 요건이 있는가 → 있으면 이것이 최상위 제약",
    "2. 데이터가 실제로 존재하는가 → 없으면 수집 체계부터 (AI는 그 다음)",
    "3. 고객 조직에 운영 주체가 있는가 → 없으면 자동화 수준을 높여야 함",
    "4. 기존 추상화 모델로 수용 가능한가 → 불가 시 아키텍처 CR",
    "5. 1단계에서 체감 가치를 줄 수 있는가 → 없으면 범위 재조정",
    "6. 레퍼런스로 자산화 가능한가 → 불가하면 사업적 가치 재검토(Alex)",
]
```
