# Configuration Management — Team Graham v5.0
## 형상관리 및 변경코드 체계 (모든 산출물 강제 적용)

**문서ID**: `BSL-STD-CM-001`
**버전**: `v1.0.0`
**적용범위**: Team Graham이 생산하는 **모든 산출물** (문서·코드·모델·데이터·제안서)
**근거표준**: ISO 10007, IEEE 828, ASPICE SUP.8, IATF 16949 7.5

---

## 0. 원칙 — 형상관리는 선택이 아니다

> **식별되지 않은 산출물은 존재하지 않는 산출물이다.**
> 문서ID·버전·변경코드가 없는 산출물은 검토·승인 대상이 될 수 없으며, Graham은 즉시 반려한다.

**적용 이유**
- 정부과제·SI 계약에서 산출물 이력 증빙 요구
- "어느 버전이 최신인가" 혼선 제거 → Graham의 확신 반복 맹점 차단
- 변경 영향 범위 추적 → Scope Creep 자동 감지

## 2. 버전 체계 (Semantic Versioning)

### 2-1. 형식

```
v{MAJOR}.{MINOR}.{PATCH}

예: v1.0.0 → v1.1.0 → v1.1.1 → v2.0.0
```

### 2-2. 버전 증가 규칙 — **승인권자가 다르다**

| 구분 | 증가 조건 | 예시 | **승인권자** |
|------|----------|------|------------|
| **MAJOR** (v1→v2) | 승인된 Baseline 변경 / 범위·아키텍처·요구사항 변경 / 게이트 재상정 필요 | 요구사항 3건 추가, 아키텍처 계층 변경 | **Graham (필수)** |
| **MINOR** (v1.0→v1.1) | 내용 보완·추가, Baseline 훼손 없음 | 설명 추가, 예시 보강, 표 추가 | Sam(기술) / Alex(사업) 리드 |
| **PATCH** (v1.0.0→v1.0.1) | 오탈자, 서식, 링크 수정 — 의미 변화 없음 | 오타 수정, 표 정렬 | 작성자 자체 |

**판단이 애매하면 상위 등급으로 올린다.** (MINOR인지 MAJOR인지 모르겠으면 MAJOR)

### 2-3. 문서 상태 (Status)

```
DRAFT      →  REVIEWED  →  APPROVED  →  BASELINED  →  SUPERSEDED
작성중        검토완료      승인완료      기준선설정     구버전(대체됨)
                 │
                 └→ REJECTED (재작성)
```

## 3. 변경코드 (Change Code) — **v5.0 핵심 신규 규칙**

### 3-1. 변경코드 형식

```
CR-{YYYYMMDD}-{NNN}

CR        Change Request 고정
YYYYMMDD  변경 발생일
NNN       당일 일련번호 (001~999)

예: CR-20260809-001
```

### 3-2. **모든 산출물 갱신 시 변경코드 부여 의무**

산출물이 갱신될 때마다 **예외 없이** 변경코드를 부여하고 변경이력 표에 1행을 추가한다.
변경코드 없는 갱신본은 **무효**이며 Graham은 검토 없이 반려한다.

### 3-3. 산출물 헤더 표준 (모든 문서 최상단 필수)

```markdown
---
문서ID: BSL-SOLTAI-SRS-001
제목: SOLT-AI 요구사항 명세서
버전: v1.2.0
상태: APPROVED
작성자: Sam
검토자: Peter, Tank
승인자: Graham
최초작성일: 2026-03-01
최종변경일: 2026-08-09
최종변경코드: CR-20260809-001
Baseline: BL-G1-20260315
---
```

### 3-4. 변경이력 표준 (모든 문서 최하단 필수)

```markdown
## 변경 이력 (Change History)

| 변경코드 | 버전 | 변경일 | 변경자 | 변경 유형 | 변경 내용 | 영향 범위 | 검토자 | 승인자 |
|---------|------|--------|--------|----------|----------|----------|--------|--------|
| CR-20260301-001 | v1.0.0 | 2026-03-01 | Sam | 신규 | 최초 작성 | - | Peter, Tank | Graham |
| CR-20260412-002 | v1.1.0 | 2026-04-12 | Sam | 보완 | 성능 요구사항 측정조건 추가 | REQ-OEE-003 | Tank | Sam |
```

## 5. Baseline 관리

### 5-1. Baseline 코드

```
BL-{게이트}-{YYYYMMDD}

예: BL-G1-20260315   요구사항 기준선
    BL-G2-20260402   아키텍처 기준선
    BL-REL-20260701  릴리스 기준선
```

### 5-2. Baseline 설정 시점

| Baseline | 설정 시점 | 포함 형상항목 |
|----------|----------|-------------|
| `BL-G0` | Concept 승인 | 사업기회 정의서, 시장분석서 |
| `BL-G1` | 요구사항 승인 | SRS, PRD, RTM 초판 |
| `BL-G2` | 아키텍처 승인 | ARCH, DBS, INF, ADR |
| `BL-G3` | 상세설계 승인 | DD, API, FMEA |
| `BL-SPR{NN}` | 각 Sprint 종료 | 소스코드 태그, Sprint Note |
| `BL-REL` | 릴리스 | 전체 형상항목 스냅샷 |

**Baseline 설정 후 해당 문서는 잠긴다(Frozen). 변경하려면 CR을 거쳐야 한다.**

## 8. 자동 점검 규칙 (에이전트 강제 수행)

**Alex·Sam·Peter·Tank는 산출물을 생성/갱신할 때마다 아래를 자동 수행한다.**

```python
CM_MANDATORY_CHECKS = [
    "문서ID가 BSL-{PROJ}-{TYPE}-{SEQ} 형식으로 부여되었는가",
    "버전이 Semantic Versioning 규칙에 맞는가",
    "변경코드 CR-{YYYYMMDD}-{NNN}가 부여되었는가",
    "문서 헤더(YAML)에 필수 8개 항목이 모두 있는가",
    "변경이력 표에 이번 변경 행이 추가되었는가",
    "MAJOR 변경인데 Graham 승인 없이 진행하려 하지 않는가",
    "Baseline 설정된 문서를 CR 없이 수정하려 하지 않는가",
    "CMDB 대장이 갱신되었는가",
]
```

**위반 시 산출물을 제출하지 않고, Graham에게 위반 사항을 먼저 보고한다.**

### 자동 보고 형식

```
⚠️ 형상관리 위반 감지
- 대상: BSL-SOLTAI-ARCH-001
- 위반: Baseline(BL-G2) 설정 문서를 CR 없이 수정 시도
- 필요 조치: CR 발행 → 영향분석 → Graham 승인
- 제안: CR-20260809-002 초안을 작성했습니다. 검토 후 승인해 주십시오.
```
